## 可核验的计算部分

实现：[astro_basis.py](../src/doonook_chinese_calendar/services/astro_basis.py)。

1. 默认读取包内 `data/de440s.bsp`；可用 `ASTRO_EPHEMERIS_PATH` 显式覆盖。计算太阳、月亮、水星、金星、火星、木星、土星。
2. 观测中心为地心，使用视位置、当日真黄道/真春分点坐标框架（Skyfield `ecliptic_frame`）。
   天体系统的火星/木星/土星使用星历中的barycenter，其他天体用中心。
   框架定义见[官方文档](https://rhodesmill.org/skyfield/api-framelib.html)。
3. 热带黄道：黄经每30°划为一个星座；这里的星座区段不是IAU天文学星座边界。
4. 每天按配置时区的12:00采样，内部转换UTC。日/月/年边界也按该时区解释。
5. 今明天分别计算；周从周一至周日；月覆盖自然月全部日期；年覆盖自然年全部日期。
   周/月/年分别汇总所有每日采样，包含闰日，不使用单日信息替代整段期间。
6. 这是固定时间快照，不搜索精确相位时刻或整日入宫事件；日内快速月亮相位可能漏采。
   目前不计算逆行、上升、出生宫位、个人本命盘或相位渐入/渐出。

请求年份支持1900–2099；缺文件、数据损坏或日期不支持时，生成返回503。
运行时不下载星历/闰秒文件，不回退到随机文案。按文件路径/年份/时区缓存计算，
更新星历文件时须重启进程；建议版本化文件名，避免原地覆盖已加载文件。

## 解释规则 solar-whole-sign-v1

这是可复现、可调整的产品编辑规则，分数不由模型决定，不是概率或经验证的预测指标。

- 五类相位及容许度：合相0°±8°、六合60°±4°、刑相90°±6°、拱相120°±6°、冲相180°±8°。
- 角距取0–180°最短弧；相位贡献乘 `1 - 偏差/容许度`，边界贡献为0。
- 六合基础贡献+0.6，拱相+1，刑相/冲相−1。合相包含火星/土星时−0.6，
  否则包含金星/木星时+0.6，其余为0；这只是本版本明示的解释取舍。
- 每领域采用涉及以下任意相关天体的相位，并采用其落入指定太阳整宫的因素：

| 领域 | 相关天体 | 关注太阳整宫 |
|---|---|---|
| love | 月亮、金星 | 5、7 |
| career | 太阳、水星、火星、土星 | 6、10 |
| money | 金星、木星、土星 | 2、8 |
| health（日常状态） | 太阳、月亮、火星 | 1、6、12 |

太阳整宫把用户选择的太阳星座设为第1宫，其后每个黄道星座依次递增；不是出生时刻的宫位。
对应落宫贡献：太阳/水星+0.2、月亮+0.1、金星/木星+0.35、火星−0.2、土星−0.35。
因此同一天的公共行星相位相同，不同太阳星座的落宫因素可以不同；不保证十二星座评分都不同。

各领域当天贡献求和后限制在[-2,2]，期间取每日贡献平均，再加中性基线3、四舍五入到1–5。
无显著因素时接近3，不人为给每期制造大起大落。因素列表保存观测天数、代表日期、
该日期的相位偏差，以及相对于全期间的平均贡献；原始分数也保存用于审计。

## 模型与数据库边界

Qwen只接收各期评分及各领域绝对平均贡献最大的两个因素。提示要求低分偏谨慎、高分偏主动，
避免把采样当天相位说成整月/整年持续；文字不复述度数/宫位，也不新增天象。
星历和评分不由模型生成。模型文案仍可能偏离提示；结构校验不等于语义准确性保证。
当前没有宣称自动验证每句文案与规则的一致性。

原来的幸运颜色/数字/贵人星座字段仍属兼容旧界面的娱乐文案，不声称由天文数据证明。
日期、星座编号/名称仍由服务端控制，JSON完整校验后入库。
Ollama MLX偶发返回“草稿JSON → </think> → 最终JSON”；仅在两者都符合完整schema时取最终对象。
此外兼容单JSON末尾的协议标记；不容忍任意解释文字、错字段或无标记的多个JSON。

- 公共API沿用原有 today/tomorrow/week/month/year 字段和响应结构，不暴露调试数据。
- 在原有五个JSON列内增加内部 `_basis` 字段，保存规则版本、星历SHA256、区间、采样方式、
  分数、所有聚合因素；今明天额外保存七个天体的位置。无需增加表列或迁移。
- Pydantic公共响应忽略 `_basis`，已有客户端无需改动。数据库记录可追溯到文件和规则版本。
- 已有缓存保持原内容；旧记录没有 `_basis`，不代表使用新规则。未自动删除或覆盖业务缓存。
- writer仍按宿主.env中的节点角色/REMOTE_WRITER_HOST选择；没有更改共享POSTGRES_HOST。

## 部署与本机查看

本包沿用 **PyPI发布 → pip安装** 的部署方式：

```bash
pip install --upgrade doonook-chinese-calendar==0.1.4
```

Skyfield等依赖由pip处理，星历文件随包安装。无需在Docker中额外COPY数据文件、运行时下载，
也无需配置Mac或服务器专属星历路径。宿主仍须升级其固定版本与重建基础镜像。

`ASTRO_EPHEMERIS_PATH` 默认为空，自动使用包内星历。只有要替换星历时才配置它；
显式配置了不存在/损坏的文件会报错，不会悄悄回退。
模型URL、key、模型名、数据库角色仍从宿主私有.env读取，绝不随包分发。
本机项目.env/.env.local已移除旧的绝对星历路径；宿主doonook_temp/.env未修改。

构建与发布：

```bash
poetry build
python scripts/check_distribution.py
poetry publish
```

发布检查针对pyproject当前版本，验证wheel/sdist中的星历SHA256、NOTICE、无私有dotenv；
旧版本dist产物保留，不参与本次检查。GitHub版本标签/manual workflow先构建和检查，再发布，
不再为打包而安装全部业务依赖。必须把代码、星历和NOTICE一并提交到发布来源。
推送与包版本一致的标签（例如v0.1.4）触发发布；标签与pyproject版本不一致时中止。
原黄历依赖sxtwl在部分ARM/Python组合的安装限制仍见README，和星历文件打包无关。

本机 [Swagger](http://127.0.0.1:8008/docs) 中新增仅开发入口提供的：

`GET /debug/astro-basis/1?date=2026-09-17`

它返回计算依据，不调用模型、不写数据库，也未挂到生产包的公开路由。
然后调用原星座接口看文案。[本轮今日依据](examples/astro-basis-2026-09-17.json)，
[完整文案样例](examples/qwen-fortune.json)。旧本机进程已重启，新临时库没有历史随机文案缓存。
